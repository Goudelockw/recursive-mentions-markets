Trades every morning. Everything else once a week.

With about a dozen markets settling each week, a daily evaluation would mostly repeat itself and keep the database awake. So the daily work is one short read of the board, turned into a trade sheet. Health checks, grading, fixes, research and cleanup all run as one batch on Sunday night.

What each column tells you

  • Do: the board's action and which side to buy. SKIP rows appear only when the risk model blocked a trade the model wanted.
  • Edge and stake: after fees, at 1/8 Kelly within the 2% per-market and 6% per-call caps.
  • Favorite, avoid points, risk tier: straight from v_open_risk_screen.
  • vs. risk model: Aligned means the model fades a favorite the risk model distrusts (backtest +13.5¢). Conflict means the two disagree, so it's skipped.
  • Preflight line: if it isn't green, don't trade off the sheet until you've checked the board.

An optional second run in the afternoon could cover Entry 2, once releases are filed. Leave it out to start and add it if you find yourself checking manually.

Naming rules

  • Dates first, ISO format: 2026-10-27_ for daily, 2026-W44_ for weekly.
  • Then the output type, in lowercase kebab-case: _trade-sheet, _weekly-review.
  • Experiments get a permanent ID and a slug: EXP-0007_news-volume.
  • Models are versioned with their fit date: v8_2026-11-01. The version matches model_coefficients.model_version.
  • Every output is committed to the repo, so you can browse history on GitHub. The Trade Sheet and Weekly Review are also pinned as pages.

Librarian does it, logs it

  • Rename or move outputs that break the naming rules
  • Move outputs older than 90 days into archive/
  • Delete Neon experiment branches older than 30 days that aren't attached to an open PR
  • Update SYSTEM.md when a job, view or rule changed that week

Librarian opens a PR

  • Remove dead code or duplicate scripts
  • Drop SQL views nothing has read in 60 days (it shows the evidence)
  • Consolidate overlapping docs

Librarian asks you

  • Deleting any table or data in kalshi
  • Closing PRs or branches someone else opened
  • Anything in Railway settings or secrets
Sunday Ops task

Fixing data gaps and pipeline errors, once a week

The checks look back over the whole week, so a once-a-week run catches the same gaps a daily run would. Anything urgent during the week shows up in the Trade Sheet's preflight line.

Fixes it, then tells you

  • Re-run failed jobs or refresh-chain steps
  • Missing transcripts: Fortune, then Equibles backfill
  • precall --refetch-missing, sweep
  • Label words the weekly labeler missed

Writes the fix, you merge

  • Bug fixes in kalshi-worker
  • A new health check for each new kind of failure
  • Timeouts, parsers

Drafts it, you decide

  • Call-time overrides that disagree with the ticker date
  • Risk overrides, trading rules, avoid points
  • Coefficients, k, sizing caps, fees
Getting better

When the live model changes

The refit runs every week, but the live model changes only on evidence. Your backtest was walk-forward by month, so that is the procedure it supports.

Normal: end of season

  • The weekly challenger is compared with the live model in the Weekly Review: coefficient and k drift, backtest Brier and ¢/trade
  • Switch at the end of each season, or sooner if the coefficients drift materially
  • You approve the switch

Fast track: clearly better

  • Beats the live model on the sealed holdout by more than the bar for the number of ideas tried
  • Holds in both periods and in 90%+ of resamples
  • Leakage review finds nothing, and there's a reason it should work
  • Goes live right away at half stake, with automatic rollback if live results leave the backtest's range

Not a model change: a fix

  • A wrong feature, bad data or a leakage bug
  • Ships as a fix PR straight away
  • The Weekly Review notes which past trades it affected

Accurate information

Checks at two levels

Every morning, in the Trade Sheet

Only the markets on today's sheet, so it costs almost nothing.

  • Pipeline: sync, filings, reconcile and transcripts ran on time, and quotes are current. If not, the sheet says STOP
  • Each market: transcript history, a fundamental score, a fresh quote, valence and incentive labels. A failure marks the row DATA ISSUE and lists it under Needs you
  • Each call: an estimated call time in the entry window, a passed call with no release, a call over its 6% cap

Every Sunday, in the weekly batch

  • The pipeline ran: job freshness, refresh-chain failures, settlement lag, missing precall prices
  • The data is complete: transcripts for every settled call, releases matched to the right quarter, speaker roles resolved, Q&A present, no missing labels
  • The data is accurate: each settled result checked against our own transcript count. If we count the word and the market settled NO, or the reverse, the transcript or the word matching is wrong. Also estimated vs. actual call times, feature ranges and drift, and a sample of labels re-checked
  • The model is healthy: calibration by price range, live vs. backtest ¢/trade, coefficient age
Keeping Neon cheap

Where the database cost comes from

What this plan adds

  • Daily: one read of the board on weekdays, about two minutes of compute.
  • Weekly: one batch on Sunday night, with every job back to back so the database wakes once.
  • Live grading snapshots the board when the Trade Sheet runs. That's the moment you trade, so it replaces the 15-minute score-log cron from v1.
  • Experiments run on Neon branches, which are deleted after 30 days.

Done Oct 27: the pipeline

  • Neon had been awake since Sep 20: about 748 CU-hours (~$79) in 26 days, plus 34 GB stored.
  • Causes: a 5-minute Atlanta-weather snapshot, an hourly pull of all of Kalshi, and a 2.9-hour nightly reconcile over ~294,000 markets.
  • Fixed: mentions-only sync and reconcile, snapshot off, non-mention data deleted (34 GB → 2.3 GB).
  • Next: the 18-step refresh chain still runs after every sync and filings run. The Sunday cost report will measure it.
